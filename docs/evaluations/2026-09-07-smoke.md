# Smoke run, 2026-09-07 — the first live evaluation

Ten questions, one repeat, `anthropic/claude-haiku-4.5`, corpus `a3364acbfa69fe90`
(14,294 entries), code `git 670cda4`. Prompt digest `f8c6e7484a570bab`.
$0.13 for ten questions, 5.7 retrievals each, all ten answered with no failures.

Run to prove the harness end to end before spending on repeats. It did that — and it
found four things, of which the first invalidates a check that is already merged and
already has an ADR. **None of the figures below should be quoted as a baseline**: one
repeat measures a trajectory, and two of the four findings change what the figures mean.

## 1. The outlier check cannot fire on this corpus, and never could

Peers were defined as *the corpus's other entries recording the same property for the
same organism*, with `property` compared as an identical string. Measured against the
real corpus:

- 10,846 distinct (property, organism) pairs carry a usable value.
- **Zero** of them hold five or more entries. The largest holds three.
- 10,753 of the 10,846 hold exactly one entry.

So `MIN_PEERS = 4` makes the check dead code, not merely quiet. The cause is that
`property` is free text and not a controlled vocabulary: `Nuclear volume (average)`,
`Volume of Nucleus`, `Volume of nucleus` and `Volume of nuclei during G1 phase` are
four distinct strings for one quantity, and `resolve_property("Nuclear volume")` alone
returns 14 stored spellings.

This is exactly what task 4.10 exists for, and what ADR-0520 said its two numbers were
waiting on — but the finding is larger than the threshold. **The comparison form is
wrong, not just the factor.** ADR-0520 needs superseding rather than amending.

The measured alternative: peers as *the entries the question's own property terms
select, restricted to the cited entry's organism*. Pool sizes per question in this set
are 4, 5, 8, 8, 16, 26, 28 and 44 — enough to judge. The organism restriction is not
optional: `yeast-vs-ecoli-volume`'s pool of 44 spans two organisms whose cell volumes
differ by more than an order of magnitude, and pooling them would flag every entry of
the smaller organism as an outlier below the larger one.

The cost of that definition is that an outlier becomes a fact about *the entries this
question asked for* rather than about the corpus, which is a weaker claim than the spec
requirement's wording.

## 2. The question set's expected lists are too narrow, for the same reason

Sixteen citations were "unexpected" against fifteen expected ones cited — and reading
them, most are correct. For `yeast-nuclear-volume` the agent cited six entries recording
nuclear volume under spellings my search for `property="Nuclear volume"` never
returned, four of them per cell-cycle phase. So the 62% citation rate understates the
agent, and the "19 of 31 cited entries carry the asked property" figure is mostly a
vocabulary artefact rather than the object-versus-measure confusion it looks like.

Two of the twelve do look like real misses: a `Median cell size` entry cited for a
volume question, and a `Size of ribosome` entry for a different organism than either
asked.

**Expected entries are frozen into each record at run time**, so this has to be fixed
*before* a baseline rather than re-scored after one — unlike a scoring rule, which the
record's raw material lets us change freely.

**And it has to be fixed from the corpus, not from what the agent cited.** Widening a
set to include the entries the system found is how a set becomes one the system passes
by construction — the failure the question-set module's own docstring warns about. The
agent's citations say where to look; the corpus vocabulary says what belongs.

## 3. A question the corpus can answer was refused

`ecoli-nucleus` returned "I could not find any data on the volume of a nucleus in
E. coli cells". Entry 100013 records exactly that quantity, under a property naming the
nucleoid. The agent searched for the organism and never for a matching property.

A real retrieval failure, found by the set on its first outing, and the one question in
the set written to require a caveat rather than a number. It also inflates
"refusals that searched first" from 2 to 3, which is why that count read oddly.

## 4. A correct follow-up is reported as a grounding failure

`ecoli-ribosomes-stationary` cited entry 114927 and the agent emitted a
`CitationWarning` marking it **unretrieved** — because the entry was retrieved during
the *parent* question, not this one. The follow-up made no search of its own at all,
which is legitimate: that is what a follow-up sharing a session is for.

So "unretrieved" means two different things in a session, and only one of them is a
failure. The harness should tell "cited without retrieval anywhere in this session"
apart from "retrieved earlier in the session", or every correct follow-up will score as
a grounding failure. The asked-terms score has the same shape of problem: the follow-up
reads as having searched for neither the organism nor the property, because it correctly
searched for nothing.

## 5. Both retrieval bounds have large headroom (task 5.2, first reading)

No question reached any limit. 5.7 retrievals per question against `TOOL_CALL_LIMIT`
of 20; the most model calls any question used was 3 against `RUN_CALL_LIMIT` of 12.
On this evidence both bounds are far from binding, and the question 5.2 poses —
whether an answer produced at a bound scores worse — cannot be answered because no
answer was produced at one. Repeats may change that; a harder question set certainly
would.

## What this run does *not* say

Nothing about run-to-run variation: one repeat cannot distinguish an improvement from a
lucky trajectory, which is why the spec requires repeats. Nothing about answer quality
beyond citations — no value was checked against its entry, and no answer was read by a
person. The hand labels of task 5.4 are the missing instrument, and they are what the
judged layer's agreement is measured against.
